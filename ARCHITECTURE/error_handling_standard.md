# SecretTalk — Error Handling Standard

## 1. Назначение

Этот документ определяет единый подход к обработке ошибок SecretTalk.

## 2. Основной принцип

Ошибка должна:

- быть обнаружена;
- иметь понятную причину;
- корректно обрабатываться;
- не разрушать работу остальных модулей;
- не скрываться без причины.

## 3. Module Errors

Модуль отвечает за ошибки своей бизнес-логики.

Он не должен самостоятельно перехватывать глобальные ошибки приложения без необходимости.

## 4. Router Errors

Router отвечает за ошибки маршрутизации:

- неизвестный route;
- некорректное состояние;
- отсутствующий handler;
- недоступный модуль.

Router не должен скрывать архитектурные ошибки.

## 5. Index Errors

`index.js` отвечает за ошибки верхнего уровня приложения:

- startup;
- initialization;
- transport;
- глобальные необработанные ошибки.

## 6. External Services

Ошибки внешних сервисов должны обрабатываться явно.

Например:

- AI provider unavailable;
- database unavailable;
- Telegram API error;
- timeout.

Пользователь должен получить корректный ответ, если это необходимо.

## 7. User Input

Некорректный пользовательский ввод не должен приводить к падению приложения.

Необходимо проверять обязательные значения до выполнения операции.

## 8. Logging

Ошибка должна быть записана в log в объёме, достаточном для диагностики.

Не записывать:

- tokens;
- passwords;
- API keys;
- чувствительные пользовательские данные.

## 9. Error Propagation

Ошибка передаётся вверх только до слоя, который действительно может её обработать.

Не следует:

- silently ignore;
- бесконечно retry;
- дублировать одну и ту же обработку ошибки на нескольких слоях.

## 10. После ошибки

Если ошибка появилась во время интеграции:

STOP.

Не делать случайные изменения.

Определить:

`WHERE FAILED`

↓

`WHY FAILED`

↓

`WHAT OWNS THE FAILURE`

↓

`MINIMAL FIX`

↓

`VERIFY`

## 11. Production

После deploy необходимо проверить logs и реальный пользовательский flow.

Если production ошибка обнаружена:

1. определить причину;
2. остановить дальнейшие изменения;
3. исправить установленную причину;
4. повторить verification;
5. commit;
6. deploy;
7. production test.

## 12. Главное правило

Ошибка должна быть локализована владельцем соответствующей ответственности.

`MODULE → MODULE ERROR`

`ROUTER → ROUTING ERROR`

`INDEX → APPLICATION ERROR`

`SERVICE → SERVICE ERROR`

Нельзя исправлять ошибку в случайном другом слое только потому, что это быстрее.
