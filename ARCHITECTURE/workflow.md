# SecretTalk — Development Workflow

## 1. Обязательный порядок работы

Каждая новая функция, модуль или архитектурное изменение выполняется только в следующем порядке:

CREATE
→ VERIFY
→ ROUTER
→ MENU
→ INDEX IF REQUIRED
→ REMOVE OLD
→ TEST
→ COMMIT

Нельзя пропускать этапы без явного архитектурного решения.

## 2. CREATE

Создать новую реализацию в её собственном модуле.

Не изменять старую реализацию вместо создания нового модуля, если задача предусматривает создание нового модуля.

## 3. VERIFY

Проверить новый модуль независимо от приложения.

Проверить:
- загрузку модуля;
- публичный интерфейс;
- зависимости;
- отсутствие синтаксических ошибок;
- ожидаемый результат работы.

## 4. ROUTER

Подключить модуль к `router.js`.

Router должен только определить, когда передать управление модулю.

Стандартная точка входа:

`module.handle(bot, msg)`

## 5. MENU

Если функция доступна пользователю через кнопку или команду, её пользовательская точка входа должна быть зарегистрирована в `menu.js` или соответствующем UI-слое.

Каждая пользовательская точка входа должна иметь одного владельца.

## 6. INDEX

`index.js` изменяется только тогда, когда модулю действительно требуется регистрация на уровне запуска приложения.

Нельзя переносить бизнес-логику модуля в `index.js`.

## 7. REMOVE OLD

После успешного подключения новой реализации старая реализация этой же функции должна быть удалена.

Запрещено оставлять одновременно активными старую и новую реализации.

## 8. TEST

Проверяется полный пользовательский путь:

USER
→ MENU
→ ROUTER
→ MODULE
→ RESULT

Проверяется также возврат назад и переходы между экранами, если они существуют.

## 9. COMMIT

После успешной проверки выполняется отдельный commit.

Commit должен отражать завершённое изменение.

## 10. Архитектурное правило

Если перед началом работы неизвестно:
- какой модуль является владельцем функции;
- куда он подключается;
- существует ли старая реализация;
- нужен ли Router;
- нужен ли Menu;
- нужен ли index.js;

сначала проводится архитектурная проверка.

Разработка не начинается методом предположения.

## 11. Источники правил

Перед архитектурными изменениями используются:

`ARCHITECTURE/architecture.json`

`ARCHITECTURE/governance.md`

`ARCHITECTURE/workflow.md`

Эти документы являются обязательной частью процесса разработки SecretTalk.
