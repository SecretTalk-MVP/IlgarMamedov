# SecretTalk — Module Registry Standard

## 1. Назначение

Этот документ определяет единый реестр модулей SecretTalk.

Каждый функциональный модуль должен иметь понятный статус, владельца и точку интеграции.

## 2. Обязательные сведения

Для каждого модуля необходимо определить:

- имя;
- расположение;
- назначение;
- главный файл;
- публичный entrypoint;
- Router route;
- Menu entry, если требуется;
- Index integration, если требуется;
- зависимости;
- статус.

## 3. Статусы

Допустимые статусы:

`ACTIVE`

Модуль работает и является авторитетной реализацией.

`INTEGRATED`

Модуль полностью подключён и протестирован.

`DEVELOPMENT`

Модуль создаётся или изменяется.

`LEGACY`

Старая реализация, ожидающая миграции или удаления.

`REFERENCE`

Материал для архитектурного использования, не runtime-код.

`UNUSED`

Файл или модуль существует, но не используется приложением.

`OBSOLETE`

Реализация окончательно заменена и может быть удалена.

## 4. Единственный владелец

Одна функция должна иметь одного авторитетного владельца.

Если обнаружены два владельца одной функции:

STOP.

Необходимо определить, какая реализация является новой и какая должна быть удалена.

## 5. Router registration

Каждый user-facing модуль должен иметь зарегистрированный маршрут.

Отсутствие Router registration означает:

`NOT INTEGRATED`

Даже если файлы модуля существуют.

## 6. Menu registration

Если модуль имеет пользовательскую кнопку или команду, она должна быть зарегистрирована и связана с Router.

Наличие только кнопки или только handler не считается интеграцией.

## 7. Index registration

Index registration указывается только для модулей, которым требуется root-level lifecycle integration.

Обычный пользовательский модуль подключается через Router.

## 8. Реестр и код

Реестр не заменяет Router и не выполняет бизнес-логику.

Он описывает архитектурное состояние проекта.

Будущий Architecture Governance Layer может использовать этот реестр для автоматической проверки.

## 9. Изменение статуса

После каждого значительного архитектурного изменения статус модуля должен соответствовать реальному состоянию кода.

Нельзя оставлять:

`ACTIVE`

если модуль уже заменён.

Нельзя считать модуль:

`INTEGRATED`

если его пользовательский путь не протестирован.

## 10. Главное правило

Факт существования папки или файла не означает наличие рабочего модуля.

Рабочий модуль определяется цепочкой:

`MODULE → ENTRYPOINT → ROUTER → USER FLOW → TEST`

Только после успешного прохождения этой цепочки модуль считается интегрированным.
