# SecretTalk — Security Standard

## 1. Назначение

Этот документ определяет базовые правила безопасности разработки SecretTalk.

## 2. Secrets

Секреты и credentials запрещено хранить в исходном коде.

К ним относятся:

- API keys;
- bot tokens;
- database passwords;
- private credentials;
- authentication secrets.

Они должны храниться через безопасную конфигурацию окружения.

## 3. Environment

Production credentials не должны попадать в:

- Git;
- documentation;
- logs;
- error messages;
- screenshots;
- test fixtures.

## 4. User Data

Персональные данные пользователя должны использоваться только там, где они необходимы функции.

Не следует сохранять данные без определённой цели.

## 5. Memory

AI memory должна сохранять только данные, которые разрешены архитектурой и необходимы для работы функции.

Не следует превращать каждое сообщение пользователя в долговременную память.

## 6. Access Control

Административные функции должны иметь отдельную проверку прав.

Обычный пользователь не должен получать доступ к Admin functionality только через знание команды или callback.

## 7. Input

Пользовательский ввод нельзя считать доверенным.

Перед использованием необходимо учитывать:

- пустые значения;
- неожиданный тип;
- слишком длинные значения;
- специальные символы;
- потенциально опасные данные.

## 8. Database

Database queries должны использовать параметризованные значения.

Не следует собирать SQL-запросы через небезопасную конкатенацию пользовательского ввода.

## 9. Logging

Logs не должны содержать:

- API keys;
- passwords;
- tokens;
- чувствительные пользовательские данные.

## 10. Module Security

Модуль должен использовать только необходимые зависимости.

Нельзя предоставлять внешнему пользователю доступ к внутренним функциям модуля без явного entrypoint.

## 11. Legacy Security

При миграции необходимо проверять, не оставляет ли старый код:

- активные credentials;
- старые API calls;
- старые privileged routes;
- неиспользуемые security bypasses.

## 12. Verification

Перед завершением security-sensitive изменения необходимо проверить:

- authentication;
- authorization;
- input handling;
- database access;
- secrets;
- logs;
- legacy references.

## 13. Главное правило

Безопасность не должна добавляться после архитектуры.

Она является частью архитектуры и проверяется одновременно с функциональностью.
