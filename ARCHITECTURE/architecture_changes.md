# SecretTalk — Architecture Change Standard

## 1. Назначение

Этот документ определяет порядок изменения самой архитектуры SecretTalk.

Изменение архитектуры отличается от обычного изменения функциональности.

## 2. Что считается архитектурным изменением

Архитектурным изменением является изменение:

- `index.js`;
- главного `router.js`;
- структуры `modules/`;
- правил интеграции модулей;
- владельца функции;
- системы навигации;
- общих сервисов;
- способов хранения состояния;
- способов взаимодействия между модулями;
- Architecture Governance Layer.

## 3. Перед изменением

Сначала определить:

1. Почему существующая архитектура недостаточна.
2. Какую проблему решает изменение.
3. Какие компоненты затронуты.
4. Какие старые компоненты будут заменены.
5. Какие модули могут быть затронуты.
6. Как будет проверено новое решение.

## 4. Запрет скрытых архитектурных изменений

Нельзя изменять архитектуру незаметно в рамках обычной задачи.

Если для реализации функции требуется изменить архитектурный принцип:

STOP.

Сначала фиксируется архитектурное решение.

## 5. Архитектурное решение

Архитектурное изменение должно определить:

`CURRENT ARCHITECTURE`

↓

`PROBLEM`

↓

`PROPOSED ARCHITECTURE`

↓

`MIGRATION`

↓

`VERIFICATION`

↓

`OLD ARCHITECTURE REMOVAL`

## 6. Обновление источников архитектуры

После утверждения архитектурного изменения необходимо обновить соответствующие:

- `ARCHITECTURE/architecture.json`;
- `ARCHITECTURE/*.md`;
- `PROJECT_DEVELOPMENT_CONSTITUTION/*`, если изменяется обязательное правило.

Документация не должна оставаться в старом состоянии после изменения архитектуры.

## 7. Миграция

Архитектурные изменения выполняются поэтапно:

1. Создать новую структуру.
2. Проверить новую структуру.
3. Подключить новую структуру.
4. Проверить полный flow.
5. Удалить старую структуру.
6. Проверить отсутствие старых ссылок.
7. Commit.
8. Deploy.
9. Production test.

## 8. Запрет параллельной архитектуры

Нельзя создавать вторую архитектуру рядом с первой только потому, что первая неудобна.

После миграции старая архитектура должна быть удалена из активного приложения.

## 9. Router

Если архитектурное изменение касается Router:

- должен оставаться один главный Router;
- маршрутизация должна оставаться отделённой от бизнес-логики;
- пользовательские entrypoints должны быть явно зарегистрированы;
- существующие маршруты должны продолжать работать.

## 10. Index

Если архитектурное изменение касается `index.js`:

`index.js` должен оставаться тонким application orchestrator.

Нельзя использовать архитектурное изменение как повод перенести бизнес-логику в `index.js`.

## 11. Проверка

После архитектурного изменения необходимо проверить:

- запуск приложения;
- Router;
- Menu;
- затронутые модули;
- пользовательские entrypoints;
- navigation;
- отсутствие дублирования;
- отсутствие старых активных ссылок.

## 12. Главное правило

Архитектура изменяется только осознанно.

Мы не «чиняем» архитектуру случайными изменениями файлов.

Сначала решение.

Потом миграция.

Потом проверка.

Потом удаление старого.

Потом commit и deploy.
