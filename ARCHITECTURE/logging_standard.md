# SecretTalk — Logging Standard

## 1. Назначение

Этот документ определяет единый стандарт логирования SecretTalk.

## 2. Основной принцип

Logs должны помогать определить:

- что произошло;
- где произошло;
- какой модуль отвечает;
- почему операция завершилась ошибкой.

Logs не должны содержать секреты или ненужные персональные данные.

## 3. Уровни

Используются следующие логические уровни:

`INFO`

Нормальные события приложения.

`WARN`

Неожиданная ситуация, которая не остановила работу.

`ERROR`

Ошибка операции.

`DEBUG`

Диагностическая информация во время разработки.

## 4. Module Logging

Модуль может записывать:

- запуск;
- важные переходы состояния;
- успешные операции;
- ошибки собственной логики.

Модуль не должен логировать внутренние данные другого модуля без необходимости.

## 5. Router Logging

Router может логировать:

- выбранный route;
- изменение состояния;
- неизвестный route;
- ошибку dispatch.

Не следует логировать полный текст каждого пользовательского сообщения.

## 6. Index Logging

Index может логировать:

- запуск приложения;
- запуск основных сервисов;
- остановку;
- глобальные ошибки.

Index не должен логировать бизнес-события отдельных модулей.

## 7. AI Logging

AI-модули могут логировать:

- начало AI-запроса;
- успешное завершение;
- ошибку AI provider;
- время выполнения.

Не следует записывать в logs:

- API keys;
- tokens;
- полный пользовательский диалог;
- содержимое долговременной памяти;
- другие чувствительные данные.

## 8. Database Logging

Database errors должны содержать достаточно информации для диагностики, но не должны раскрывать:

- credentials;
- passwords;
- connection secrets.

## 9. Production

Production logs должны быть пригодны для диагностики реальных ошибок.

Debug logging не должен бесконтрольно увеличивать объём production logs.

## 10. Error Correlation

При необходимости связать несколько сообщений одной операции следует использовать идентификатор операции или запроса.

Это позволяет проследить:

`USER ACTION → ROUTER → MODULE → SERVICE → RESULT`

## 11. Запрет

Не использовать logs как замену архитектуре.

Если для понимания работы системы необходимо постоянно читать logs, архитектурный flow должен быть упрощён или документирован.

## 12. Главное правило

Logs должны объяснять поведение системы, а не становиться самой системой.
