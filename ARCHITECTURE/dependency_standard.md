# SecretTalk — Dependency Standard

## 1. Назначение

Этот документ определяет правила использования зависимостей между модулями SecretTalk.

## 2. Основной принцип

Модуль должен зависеть только от того, что ему действительно необходимо.

Зависимости должны быть явными.

## 3. Shared infrastructure

Общие сервисы могут использоваться несколькими модулями.

Примеры:

- database;
- configuration;
- logging;
- OpenRouter client;
- общие utility services.

Общий сервис не должен содержать бизнес-логику конкретного модуля.

## 4. Module-to-module

Модули не должны напрямую вмешиваться во внутреннюю реализацию друг друга.

Допустимо взаимодействие только через публичный интерфейс.

Стандарт:

`MODULE A → PUBLIC API → MODULE B`

Запрещено:

`MODULE A → INTERNAL FILE OF MODULE B`

если это не предусмотрено архитектурным контрактом.

## 5. Router dependency

Модуль не должен импортировать Router только для того, чтобы самостоятельно управлять глобальной навигацией.

Router управляет маршрутизацией.

Модуль предоставляет public entrypoint.

## 6. Index dependency

Модуль не должен зависеть от `index.js`.

Index является верхним уровнем запуска приложения.

## 7. Circular dependencies

Не допускаются циклические зависимости:

`A → B → A`

Если такая зависимость необходима, архитектура должна быть пересмотрена.

## 8. Legacy dependencies

После миграции необходимо удалить зависимости нового модуля от старой реализации.

Нельзя оставлять скрытую зависимость только потому, что старый код всё ещё существует.

## 9. Проверка

Перед завершением изменения проверить:

- все imports;
- все require;
- публичные interfaces;
- старые зависимости;
- возможные циклические зависимости;
- не используется ли старый модуль новым кодом.

## 10. Главное правило

Зависимость должна идти к владельцу функции или к утверждённой общей инфраструктуре.

Новый модуль не должен зависеть от старой реализации только ради удобства миграции.
