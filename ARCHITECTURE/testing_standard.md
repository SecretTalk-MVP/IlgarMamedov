# SecretTalk — Testing Standard

## 1. Назначение

Этот документ определяет обязательный порядок тестирования изменений SecretTalk.

## 2. Основной принцип

Изменение считается завершённым только после проверки на соответствующем уровне.

Успешный запуск приложения сам по себе не означает успешную интеграцию.

## 3. Module Test

Новый модуль сначала проверяется отдельно.

Проверить:

- загрузку;
- зависимости;
- публичный интерфейс;
- основную функцию;
- обработку ошибок.

## 4. Integration Test

После подключения проверить:

`USER ACTION → ROUTER → MODULE → RESULT`

Проверить также:

- правильный маршрут;
- правильный state;
- отсутствие дублирования;
- отсутствие вызова старой реализации.

## 5. Regression Test

После изменения одного модуля необходимо проверить связанные существующие функции.

Особенно:

- Main Menu;
- Router;
- navigation;
- Admin;
- Settings;
- другие затронутые модули.

## 6. State Test

Для stateful-модуля проверить:

`ENTER`

→ сообщение внутри модуля

→ правильный ответ

→ `EXIT`

→ сообщение после выхода

После выхода старый модуль не должен получать сообщение.

## 7. Production Test

После deploy выполнить реальный пользовательский сценарий.

Проверяется именно поведение работающего приложения.

## 8. Legacy Test

После миграции проверить:

- старый import отсутствует;
- старый route отсутствует;
- старый handler не вызывается;
- старая реализация не получает пользовательские сообщения.

## 9. Failure Test

Если возможно, проверить ожидаемые ошибки:

- отсутствует userId;
- отсутствует сообщение;
- отсутствует зависимость;
- внешний сервис недоступен;
- модуль возвращает ошибку.

Приложение не должно silently fail.

## 10. Definition of Done

Изменение считается протестированным только после:

`MODULE TEST`

→ `INTEGRATION TEST`

→ `REGRESSION TEST`

→ `PRODUCTION TEST`

если соответствующий уровень применим.

## 11. Главное правило

Не проверяем только то, что мы изменили.

Проверяем также, что изменение не сломало архитектурный путь вокруг него.
