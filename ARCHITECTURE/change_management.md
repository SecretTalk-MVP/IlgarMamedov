# SecretTalk — Change Management Standard

## 1. Назначение

Этот документ определяет единый порядок управления изменениями проекта.

## 2. Любое изменение начинается с определения

Перед изменением необходимо определить:

- что меняется;
- зачем меняется;
- кто владелец функции;
- какой модуль затронут;
- какой entrypoint используется;
- какой Router route используется;
- есть ли старая реализация.

## 3. Типы изменений

Изменение классифицируется как:

`FEATURE`

Новая функция.

`MODULE_CHANGE`

Изменение существующего модуля.

`MIGRATION`

Замена старой реализации новой.

`ARCHITECTURE_CHANGE`

Изменение архитектурного принципа.

`BUGFIX`

Исправление существующего поведения без изменения архитектуры.

## 4. Feature

Новая функция проходит:

`PREFLIGHT → CREATE → VERIFY → INTEGRATE → TEST → COMMIT → DEPLOY`

## 5. Migration

Замена старой реализации проходит:

`PREFLIGHT → CREATE NEW → VERIFY → INTEGRATE → REMOVE OLD → VERIFY → COMMIT → DEPLOY → TEST`

## 6. Architecture Change

Если изменение меняет архитектурный принцип:

`STOP → ARCHITECTURE REVIEW → APPROVAL → UPDATE STANDARD → IMPLEMENT → VERIFY`

Нельзя менять архитектурные правила молча.

## 7. Bugfix

Исправление не должно использоваться как повод для создания новой архитектуры.

Если для исправления требуется архитектурное изменение, изменение переклассифицируется как:

`ARCHITECTURE_CHANGE`

## 8. Scope

Каждое изменение должно иметь ограниченный scope.

Не следует одновременно:

- создавать новый модуль;
- менять Router;
- менять Index;
- удалять несколько legacy-систем;

если эти изменения не являются частью одного утверждённого migration plan.

## 9. Проверка после изменения

После изменения определить:

- что изменилось;
- что осталось прежним;
- что было удалено;
- какие маршруты затронуты;
- какие пользовательские сценарии необходимо проверить.

## 10. Главное правило

Не смешивать случайные изменения.

Каждый commit должен иметь понятную цель и соответствовать определённому типу изменения.
