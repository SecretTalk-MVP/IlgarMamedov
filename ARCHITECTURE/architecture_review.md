# SecretTalk — Architecture Review Standard

## 1. Назначение

Этот документ определяет единственный порядок проверки архитектуры перед изменениями.

Цель — прекратить повторные ревизии, поиск структуры и принятие решений наугад.

## 2. Когда требуется проверка

Architecture Review выполняется перед:

- созданием нового модуля;
- заменой существующего модуля;
- изменением Router;
- изменением Index;
- изменением Menu;
- переносом функции;
- удалением старой архитектуры;
- изменением общего сервиса;
- изменением архитектурных правил.

## 3. Что проверяется

Проверить:

1. текущего владельца функции;
2. текущий модуль;
3. текущий public entrypoint;
4. Router route;
5. Menu entry;
6. Index integration;
7. зависимости;
8. старую реализацию;
9. дублирующие реализации;
10. архитектурные документы.

## 4. Результат проверки

Проверка должна привести к одному из результатов:

`READY`

Архитектура понятна и изменение можно начинать.

`MIGRATION REQUIRED`

Существует старая реализация, которую необходимо заменить.

`ARCHITECTURE CHANGE REQUIRED`

Текущая архитектура не поддерживает требуемую функцию.

`BLOCKED`

Обнаружено противоречие, которое необходимо разрешить до начала работы.

## 5. Запрет повторного анализа

Если функция уже имеет утверждённый:

- модуль;
- entrypoint;
- Router route;
- integration pattern;

не требуется заново проектировать их при каждом изменении.

Используется существующий стандарт.

## 6. Новая функция

Для новой функции определяется:

`FUNCTION`

↓

`OWNER MODULE`

↓

`PUBLIC ENTRYPOINT`

↓

`ROUTER`

↓

`MENU / USER ENTRY`

↓

`INDEX IF REQUIRED`

↓

`VERIFICATION`

## 7. Замена

Для замены определяется:

`OLD IMPLEMENTATION`

↓

`NEW MODULE`

↓

`INDEPENDENT VERIFY`

↓

`INTEGRATE`

↓

`REMOVE OLD`

↓

`VERIFY`

## 8. Архитектурный конфликт

Если обнаружено противоречие между:

- кодом;
- architecture.json;
- governance.md;
- workflow.md;
- constitution;
- module standard;

работа останавливается.

Нельзя выбирать один вариант молча.

Сначала определяется актуальное архитектурное решение.

## 9. Документация

После утверждённого архитектурного изменения соответствующие архитектурные документы должны быть обновлены.

Документация не должна описывать архитектуру, которой больше не существует.

## 10. Финальный результат

После Review должно быть понятно:

- что создаём;
- что изменяем;
- что подключаем;
- куда подключаем;
- что удаляем;
- как проверяем.

После этого начинается выполнение.

## 11. Главное правило

Architecture Review не является постоянным повторным аудитом.

Его задача — один раз определить архитектурный путь для конкретного изменения.

После утверждения путь используется повторно по установленному стандарту.
