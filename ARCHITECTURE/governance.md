# SecretTalk — Architecture Governance

## 1. Назначение

Этот документ устанавливает обязательные правила разработки и интеграции проекта SecretTalk.

`ARCHITECTURE/architecture.json` является техническим источником архитектурной структуры.

Этот документ определяет порядок действий.

---

## 2. Обязательное правило

Перед созданием, изменением или подключением любого модуля необходимо проверить:

1. Где находится владелец функции.
2. Какой модуль является единственным источником логики.
3. Как модуль подключается к Router.
4. Нужна ли регистрация в Menu.
5. Нужна ли регистрация в index.js.
6. Существует ли старая реализация.
7. Не будет ли одновременно работать старая и новая реализация.

Нельзя начинать реализацию до этой проверки.

---

## 3. Стандарт создания модуля

Каждый новый модуль проходит одинаковый алгоритм:

1. Создать модуль.
2. Определить его публичный интерфейс.
3. Проверить модуль отдельно.
4. Подключить модуль к Router.
5. Подключить пользовательскую точку входа к Menu, если она существует.
6. Подключить index.js только если это действительно необходимо.
7. Удалить старую реализацию этой функции.
8. Проверить полный пользовательский сценарий.
9. Выполнить commit.

---

## 4. Router

Router отвечает только за:

- навигацию;
- определение активного экрана;
- передачу управления соответствующему модулю;
- возврат пользователя назад.

Router не должен содержать бизнес-логику модулей.

Каждый модуль должен иметь одного владельца и одну точку маршрутизации.

---

## 5. Index.js

`index.js` является оркестратором приложения.

В `index.js` запрещается:

- дублировать логику модулей;
- реализовывать функции модулей;
- сохранять старые реализации после миграции;
- создавать альтернативную маршрутизацию.

---

## 6. Menu

Каждая пользовательская кнопка или команда должна иметь:

- одного владельца;
- одну точку входа;
- один маршрут;
- один обработчик.

Нельзя оставлять кнопку без маршрута.

Нельзя иметь несколько обработчиков одной пользовательской команды без явной необходимости.

---

## 7. Старые реализации

При создании новой реализации существующая старая реализация считается временной только до завершения миграции.

После подключения нового модуля старая реализация должна быть удалена.

Запрещено оставлять одновременно:

- старый модуль;
- новый модуль;
- старый обработчик;
- новый обработчик.

---

## 8. AiDa

Авторитетная реализация AiDa:

`modules/aida/aida.js`

Память:

`modules/aida/aida.memory.js`

Характер:

`modules/aida/aida.system.md`

Старые AI-файлы не являются источником логики AiDa.

---

## 9. Проверка перед commit

Перед каждым commit необходимо проверить:

- модуль подключён;
- Router использует новый модуль;
- Menu использует правильную точку входа;
- index.js не содержит старую реализацию;
- старый модуль не вызывается;
- нет дублирующихся обработчиков;
- полный пользовательский сценарий работает.

---

## 10. Запрет на угадывание архитектуры

Если структура проекта неизвестна или неоднозначна, сначала проводится проверка архитектуры.

Нельзя:

- угадывать структуру;
- создавать альтернативную архитектуру;
- возвращаться к старой реализации;
- подключать модуль «примерно»;
- менять несколько архитектурных слоёв без проверки.

---

## 11. Обязательный алгоритм

Для каждой новой функции:

`CREATE → VERIFY → ROUTER → MENU → INDEX IF REQUIRED → REMOVE OLD → TEST → COMMIT`

Этот алгоритм является обязательным стандартом проекта.

---

## 12. Статус

Этот документ является обязательным для всех последующих изменений проекта SecretTalk.

Новый код не должен нарушать данный стандарт без отдельного архитектурного решения.
